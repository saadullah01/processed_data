Interestingly with FUZZ_VERBOSE turned on (which enables debug logging) we actually terminate sooner, in Curl_debug < Curl_pp_readresp (pingpong.c:357). But yes, very reproducible.

The stack trace shows that the FTP code accesses the data->state.buffer after it has been freed. The bad access is here:

 #0 0x5e0dde in ftp_endofresp curl/lib/ftp.c:537:19

... but the buffer is freed in multi_done (multi.c:787), *after* ftp_done has been called so I still don't see how this code executes *after* the freeing of that buffer.

2622	      if(data->state.wildcardmatch) {
2623	        if(data->wildcard->state != CURLWC_DONE) {
2626	          multistate(data, MSTATE_INIT);
2627	          break;
}

Since the connection is still there and alive, it actually will just start over the statemachine (with a new filename) and reuse the existing connection. It's not that bad.

But it triggers this problem and I think I know why:

- when the connection is setup, Curl_pp_init() is called and that stores a pointer to data->state.buffer in a ping pong struct
- then the transfer is done using that buffer
- when multi_done is called, the buffer is freed
- the wildcard logic makes the state machine start over at INIT
- when it reaches the CONNECT state it allocates a new state.buffer

And here is the issue: when it reuses the FTP connection for this, it does *not* call Curl_pp_init() again. The poingping struct remains having a pointer to the *previous* buffer which is now freed...

I'll write up a PR for this.
